## 一、方案结论

本次建议将项目架构整理为“按内容类型分层、按运行职责拆分、按风险优先级推进”的 v1 方案。

核心判断如下：

1. 当前架构仍适合继续演进，但已经从“单次脚本集合”进入“需要工程化整理”的阶段。
2. v1 不强制落地统一数据模型，不做过早的通用 pipeline 抽象。
3. v1 先解决会直接伤害数据质量与稳定性的事项，再做结构整理。
4. 新架构应能支撑现有的书籍、武器、圣遗物，并为角色、任务、剧情预留稳定扩展位。
5. `CLAUDE.md` 中定义的记录契约
   `id/title/url/namespace/source/fetched_at/content_raw/content_clean/categories/links/templates/infobox/revision`
   作为架构指导原则保留，但在 v1 中只要求作为存储与模块设计方向，不要求所有 parser 立即完全遵守。

## 三、当前问题归纳

### 3.1 已确认的高优先问题

1. 书籍正文段落边界不符合目标文档要求。
   当前 `BookParser` 将多个 `<p>` 使用 `"\n"` 拼接，目标文档要求段落间使用 `"\n\n"`。
2. 圣遗物列表页解析仍建立在假设结构上。
   当前 `ArtifactsParser.extract_artifact_links()` 仍依赖 `visible-xs` 模式，缺少真实页面样本校验。

### 3.2 已确认的中优先问题

1. 缺少统一的解析告警机制。
   目前大部分异常只体现在日志或失败文件中，没有结构化告警、规则分级和运行摘要。
2. 配置与命名空间存在漂移。
   `book_dir`、`arm_dir`、`artifact_dir`、`links_dir` 未在默认配置中统一声明。
3. 架构文档落后于代码。
   `src/linkchecker/`、`scripts/check_links.py`、`storage/links/` 尚未纳入 `doc/ARCHITECTURE.md`。

### 3.3 已识别但应延后的低优先问题

1. 统一数据模型尚未真正落地。
2. 三类爬取脚本存在重复流程。
3. 原始数据、清洗数据、结构化数据的落盘标准不统一。

以上问题都成立，但结合对抗性审查结论，v1 应按“先保数据质量与可验证性，再做结构整理”的顺序推进。

## 四、架构目标

本次架构整理的目标分为三个维度：

### 4.1 可扩展性

1. 新增一种内容类型时，不应复制整套工程骨架。
2. 角色、任务、剧情应能沿用统一的模块职责边界。
3. 类型差异保留在类型包内，共性收敛到抓取、存储、告警、运行元数据层。

### 4.2 可维护性

1. 每种内容类型拥有明确的 parser、validator、writer、脚本入口。
2. 存储路径、配置命名、失败记录、运行摘要统一。
3. 真实页面样本与测试夹具稳定沉淀，降低页面改版时的排查成本。

### 4.3 可部署性

1. 每次抓取应有可追踪的运行信息。
2. 脚本应具备稳定入口，支持后续接入定时任务、CI 或批量执行。
3. 异常、解析缺失、结构变化应能形成日志和告警，而不是只靠人工翻日志。

## 五、v1 设计原则

1. 保留“按内容类型独立演进”的策略，不强推大一统 pipeline。
2. 只抽象已经稳定的共性：抓取客户端、存储布局、告警、运行摘要、基础接口。
3. 保持脚本入口薄，复杂度下沉到 `src/` 内部模块。
4. 以真实页面样本和测试夹具约束 parser，而不是只靠说明文档。
5. 以 `namespace` 作为跨模块主键，逐步统一配置、存储、告警、链接检查命名。

│   │   ├── validator.py

### 6.2 模块职责

#### 1. `crawler/`

- 只负责请求、重试、限速、页面基础信息获取
- 不负责内容类型判断
- 为后续接入 wikitext、revision、page info 留接口

#### 2. `content/<namespace>/`

- 每种内容类型独立维护解析逻辑
- 每种内容类型独立维护校验规则
- 每种内容类型独立维护清洗与写入策略
- 角色、任务、剧情后续只需新增同构目录，不改其他类型实现

#### 3. `storage/`

- 统一定义目录布局
- 统一失败记录格式
- 统一运行摘要格式
- 统一 raw / cleaned / structured 的最小落盘规范

#### 4. `alerts/`

- 将“解析失败”“关键字段缺失”“页面结构异常”“列表抓取结果异常偏少”结构化输出
- 先支持日志和本地告警文件，后续再扩展到 webhook/消息通知

#### 5. `linkchecker/`

- 保持独立，不并入主爬取脚本
- 但应改为依赖 `content.registry` 和统一命名空间，而不是散落的硬编码映射

### 6.3 建议的数据目录布局

storage/

│   ├── cleaned/
│   ├── structured/

│   ├── cleaned/

│   └── manifests/

说明：

1. `book` / `arm` 与 `books` / `arms` 的命名不一致应被收敛。
2. 若 v1 不希望立即迁移历史数据目录，可先引入 namespace 到路径的映射表，兼容旧目录。
3. v1 至少要做到所有类型都具备一致的 raw、cleaned、structured、failed、manifests 语义。

## 八、命名空间与扩展策略

建议统一使用以下 namespace：

- `books`
- `arms`
- `artifacts`
- `characters`
- `quests`
- `stories`

新增内容类型时，仅需新增：

1. `src/content/<namespace>/parser.py`
2. `src/content/<namespace>/validator.py`
3. `src/content/<namespace>/writer.py`
4. `scripts/crawl_<namespace>.py`
5. `tests/fixtures/html/<namespace>/`
6. `tests/unit/test_<namespace>_parser.py`

8. `configs/config.yaml` 对应 namespace 的存储与抓取配置

这样可以支撑书籍、武器、圣遗物继续演进，也能平滑接入角色、任务、剧情。

## 九、代码重构详细步骤

### 阶段 A：高优先级修复

#### A1. 修复书籍段落边界

1. 修改书籍正文组装逻辑，将卷内多个 `<p>` 的拼接从 `"\n"` 调整为 `"\n\n"`。
2. 为 `<br />` 与 `<p>` 混合场景补充测试。
3. 以目标文档 `doc/target/crawl_books.md` 作为验收标准。
4. 回归检查现有已抓取书籍的 cleaned 文本表现。

#### A2. 圣遗物页面真实样本验证

1. 从真实页面保存圣遗物列表页 HTML 样本。
2. 从真实页面保存至少 2 个详情页样本，覆盖不同稀有度与获取途径结构。
3. 新增基于真实样本的 `extract_artifact_links()` 与详情解析测试。
4. 如果真实结构与 `visible-xs` 假设不一致，优先修正 parser，再允许继续扩展圣遗物数据。

### 阶段 B：中优先级收敛

#### B1. 增加告警机制

1. 定义告警等级：`info`、`warning`、`error`。
2. 建立最小规则集：
   - 列表页抓取数量为 0
   - 详情页关键字段为空
   - 圣遗物部件数不足 5
   - 书籍卷数为 0
   - writer 落盘失败
3. 每次运行输出 `manifest + alerts.json`。
4. `check_links.py` 在发现异常变化时可复用同一套告警输出。

#### B2. 统一配置与命名

1. 在 `config` 默认值中明确声明 `books/arms/artifacts/links` 的路径配置。
2. 引入 namespace 注册表，统一脚本、linkchecker、storage 的命名。
3. 收敛当前 `book_dir`、`arm_dir`、`artifact_dir`、`links_dir` 的分散定义。

#### B3. 补运行摘要

每次抓取至少记录：

- run_id
- namespace
- started_at / finished_at
- source_page
- fetched_count
- saved_count
- failed_count
- warning_count
- parser_version
- config_snapshot

### 阶段 C：结构整理

#### C1. 按内容类型重组 `src/`

建议迁移顺序：

1. 书籍模块
2. 武器模块
3. 圣遗物模块
4. linkchecker 对接 registry

迁移规则：

1. parser、validator、writer 尽量同目录共存
2. 类型相关 dataclass 也放入对应 namespace 内
3. 旧 import 先做兼容导出，避免一次性大面积改动

#### C2. 收敛存储层

1. 抽 `layout.py` 统一路径规则。
2. 抽 `failure_store.py` 统一失败记录。
3. 抽 `manifest_store.py` 统一运行摘要。
4. 三类 writer 统一支持 raw、cleaned、structured。
5. 书籍、武器、圣遗物的 writer 行为保持一致，不再出现某类只有 jsonl、某类还有 cleaned、某类缺 raw 的情况。

#### C3. 脚本瘦身

1. `crawl_*.py` 只负责组装依赖、读取配置、输出摘要。
2. 具体逻辑下沉到 `src/content/<namespace>/` 与 `src/storage/`。
3. 不在 v1 强制合并为一个通用 pipeline runner，但允许抽取少量共享 helper。

### 阶段 D：测试与部署准备

#### D1. 测试补强

1. `tests/fixtures/html/` 固化真实样本。
2. 新增 writer 落盘测试。
3. 新增最小集成测试：
   - 列表页解析
   - 单详情页解析
   - 单详情页落盘
   - manifest 生成

#### D2. 部署准备

1. 保持脚本入口稳定：`crawl_books.py`、`crawl_arms.py`、`crawl_artifacts.py`
2. 允许后续接入任务调度器时直接调用脚本
3. 配置文件保留默认值，并允许未来通过环境变量覆盖
4. 日志、告警、manifest 的输出目录固定，便于批量采集

## 十、优先级排序

严格按对抗性审查结论执行：

### 高优先级

1. 段落边界修复
2. 圣遗物页面验证

### 中优先级

1. 告警机制

### 低优先级

1. 统一数据模型
2. 通用 pipeline

说明：

1. 高优先级属于“当前继续产出数据前必须先确认或修复”的事项。
2. 中优先级属于“降低隐性风险、为后续部署做准备”的事项。
3. 低优先级属于“架构演进收益明确，但当前不应压过数据质量与验证”的事项。

## 十一、与 `CLAUDE.md` 记录契约的关系

`CLAUDE.md` 中的统一记录字段应视为 v2 目标约束，而非 v1 的一次性迁移要求。

v1 建议采用“渐进对齐”策略：

1. 先统一 `title`、`url`、`namespace`、`source`、`fetched_at` 等元字段的来源与命名。
2. raw / cleaned / structured 三层存储先统一目录语义。
3. `infobox`、`revision`、`templates`、`links`、`categories` 等字段优先在架构设计中预留位置。
4. 各 parser 当前已有的类型特定字段继续保留在各自 payload 中。

这样既不违背 `CLAUDE.md` 的方向，也不强迫当前所有 parser 立刻重写。

## 十二、建议的实施顺序

1. 先修书籍段落边界并补测试。
2. 再补圣遗物真实页面样本并完成验证。
3. 然后接入告警与 manifest。
4. 再做命名空间、配置、存储布局收敛。
5. 最后再按内容类型重组 `src/` 模块。

## 十三、验收标准

满足以下条件可认为 v1 架构整理完成：

1. 书籍段落格式符合目标文档要求。
2. 圣遗物列表与详情解析均有真实样本测试支撑。
3. 所有内容类型都有统一的失败记录和运行摘要。
4. `doc/ARCHITECTURE.md` 与代码结构一致。
5. 配置文件能完整描述 `books/arms/artifacts/links`。
6. 新增一个内容类型时，改动范围可控制在 `content/<namespace>`、脚本入口、配置和测试夹具之内。

## 十四、最终建议

本次 v1 架构整理不应追求“一次性抽象到位”，而应优先完成三个结果：

1. 数据质量可信
2. 页面结构变化可感知
3. 新类型接入有稳定骨架

在此基础上，统一数据模型与通用 pipeline 再进入 v2，会比现在直接推进更稳妥。
