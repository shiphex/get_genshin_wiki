## 审查结论

总体判断：当前项目已经能支持书籍、武器、圣遗物三个方向的抓取与解析，作为单人快速迭代工具是可用的；但如果目标是长期扩展为稳定的 Wiki 语料采集工程，当前架构还不够稳，尤其是统一数据模型、原始数据留存、通用 pipeline 和真实页面验证这几块还没有真正收敛。

## 主要问题

### 1. 高优先级：项目声明的数据契约没有落到实现

`CLAUDE.md:61-74` 已经定义了统一记录字段，要求每条记录至少包含 `id`、`namespace`、`source`、`content_raw`、`content_clean`、`categories`、`links`、`templates`、`infobox`、`revision`，并要求原始数据和清洗数据分开存储。

但当前三类数据模型都没有落到这个契约上：

- `src/parser/book_parser.py:44-68`
- `src/parser/arms_parser.py:37-56`
- `src/parser/artifacts_parser.py:55-90`

当前输出本质上仍是“按类型各自定制的 JSON 结构”，统一性不足，后续做 RAG、检索、清洗、增量更新时会出现以下问题：

- 无法统一编排下游处理流程
- 无法稳定保存原始 HTML / wikitext 以支持回溯解析
- 无法将结构化信息和全文内容稳定映射到统一 schema

同时，存储层虽然有一定目录分层，但没有真正完成“raw / cleaned”双轨落盘：

- `src/storage/writer.py:14-55` 创建了 `raw/`，但没有写入原始数据
- `src/storage/arms_writer.py:14-66` 同样创建了 `raw/`，但没有写入原始数据
- `src/storage/artifacts_writer.py:14-38` 连 `raw/` / `cleaned/` 分层都没有

而抓取入口目前只走了渲染 HTML：

- `src/crawler/client.py:101-117` 使用 `parse` 取 HTML
- `src/crawler/client.py:139-162` 虽然已有 `get_page_text()`，但主流程没有接入

这意味着项目文档中的目标和当前代码产物并不一致，这是当前最大的架构偏差。

### 2. 中高优先级：圣遗物能力仍然建立在“假设实现”上

`src/parser/artifacts_parser.py:462-467` 已经明确说明：当前圣遗物列表提取逻辑只是暂时按武器页的 `visible-xs` 模式假设实现，真实页面结构仍需验证。

但这条链路已经被正式接入主流程：

- `scripts/crawl_artifacts.py:20-30`
- `src/linkchecker/checker.py:66-92`

问题在于，现有测试并没有证明真实页面可用，只证明“代码内部的假设和测试样例一致”：

- `tests/test_artifacts_parser.py:59-84`

因此当前圣遗物模块更准确的状态应是“可运行的草案实现”，而不是“经真实页面验证后的稳定能力”。如果继续基于它做数据积累，后续很可能出现批量误抓、漏抓或链接错抓。

### 3. 中优先级：书籍正文的段落语义被压扁

目标文档 `doc/target/crawl_books.md:8-23` 明确要求：

- `<br />` 转换为 `\n`
- 段落 `<p>` 之间使用 `\n\n`

但当前实现里：

- `src/parser/book_parser.py:238-243` 逐段提取文本
- `src/parser/book_parser.py:246-249` 最终使用单个 `"\n"` 拼接各段

这样会把原本应保留的段落边界压成单换行。对于书籍、诗歌、卷内多段文本，这会直接损伤语料质量，尤其影响：

- 训练集可读性
- 分块策略
- 检索召回的语义完整性

现有测试 `tests/test_book_parser.py:35-57` 没有覆盖这一点，因此测试通过并不代表格式满足目标要求。

### 4. 中优先级：按内容类型复制实现，已经开始出现配置和行为漂移

现在的实现方式是：

- 每种内容一个 parser
- 每种内容一个 writer
- 每种内容一个 crawl 脚本

这种组织在项目早期可以接受，但当前已经出现漂移：

- `src/utils/config.py:35-54` 的默认配置只有 `book_dir`
- `scripts/crawl_arms.py:78-79` 读取 `arm_dir`
- `scripts/crawl_artifacts.py:78-79` 读取 `artifact_dir`
- `scripts/check_links.py:184` 读取 `links_dir`

也就是说，配置契约没有集中定义，部分能力依赖外部 YAML，部分依赖硬编码默认值，后续扩展角色、任务、剧情时会进一步放大维护成本。

此外，目标文档与实现也开始分叉。例如：

- `doc/target/crawl_artifacts.md:52-59` 要求 TAG 按 `、` 分条保存
- `src/parser/artifacts_parser.py:35-44` 仍将 TAG 设计为单个字符串

这说明项目目前缺少“文档约束 -> 统一 schema -> 代码实现”的闭环。

### 5. 中低优先级：文档与仓库实际状态存在漂移

`doc/ARCHITECTURE.md:7-72` 没有覆盖当前已存在的：

- `src/linkchecker/`
- `scripts/check_links.py`
- `storage/links/`

此外，`pyproject.toml:5` 声明了 `readme = "README.md"`，但项目根目录当前没有 `README.md`。

这类问题不会立刻影响运行，但会降低以下方面的可靠性：

- 新成员理解项目结构
- 自动化打包元信息完整性
- 文档作为事实来源的可信度

## 建议的优先改进顺序

### 第一阶段：先收敛数据模型

建议定义一个统一的基础记录模型，例如：

- 元数据层：`id`、`title`、`url`、`namespace`、`source`、`fetched_at`、`revision`
- 原始层：`content_raw_html`、`content_raw_wikitext`
- 清洗层：`content_clean`
- 结构化层：`infobox`、`categories`、`links`、`templates`
- 类型特定层：`payload`

这样既能保留通用性，也不会抹平书籍/武器/圣遗物的差异。

### 第二阶段：抽通用 pipeline

建议把三个入口脚本的共性收敛为统一流程：

1. 拉列表
2. 过滤已抓取 / 已失败
3. 拉详情页
4. 同时保存 raw + clean + structured
5. 记录失败和统计

按类型变化的部分只保留：

- 列表页标题
- 链接提取器
- 详情页解析器
- 类型专属 `payload`

否则项目扩展到角色、任务、剧情时，重复代码会快速失控。

### 第三阶段：补真实样本与集成测试

优先给圣遗物和书籍补真实页面样本，并建立最少量的集成级校验：

- 列表页真实 HTML 样本
- 详情页真实 HTML 样本
- 至少一条从“抓列表 -> 抓详情 -> 落盘”的集成测试

这一步会比继续堆 parser 细节更重要，因为它能验证项目是否真的在按真实页面工作。

## 最终判断

当前项目不是“架构错误”，而是“已经走到需要从脚本集合升级成工程化采集器的节点”。基础模块划分已经有雏形，但统一 schema、原始数据留存、真实页面验证和通用 pipeline 还没建立完成。

如果短期目标只是继续补几个抓取器，当前架构还能撑一段时间；如果目标是长期积累高质量 Wiki 语料并持续扩展内容类型，建议尽快进行一次围绕统一数据模型和通用抓取流程的重构。
