# 发布说明与变更日志生成器

该技能通过分析 git 仓库来生成**对最终用户友好**的发布说明和变更日志。它读取实际的代码差异（而不仅仅是提交信息），理解变更内容，整合相关变更，并生成适合 Slack 更新和项目文档的整洁 Markdown 内容。

## 核心优势

- **基于差异分析**：读取实际代码变更，而非仅仅依赖提交信息
- **关注最终用户**：输出内容不包含技术术语、函数名或变量名
- **智能整合**：若变更发生反复且最终无实际影响，则不予列出
- **仅展示最终状态**：呈现最终结果，而非中间步骤
- **破坏性变更检测**：自动识别提交和代码差异中的破坏性变更
- **跨平台**：支持 Windows、macOS 和 Linux
- **支持多种远程仓库**：GitHub、Bitbucket 及本地 git 仓库

## 功能特性

- **标签间分析**：生成任意两个发布标签之间的说明（例如：从 v1.0.0 到 v1.1.0）
- **基于上一标签**：自动检测上一个标签并展示自那时以来的变更
- **近期提交**：分析最近 N 次提交以快速生成更新内容
- **完整差异读取**：理解实际代码变更，而非模糊的提交信息
- **变更整合**：合并相关变更，剔除反复修改（来回变动）的内容
- **分类归档**：归类为：新功能、增强功能、错误修复、变更、破坏性变更、其他
- **适配 Slack 的输出**：格式化的 Markdown，包含项目符号及可选脚注
- **支持脚注**：添加设置说明或重要信息，且无需暴露敏感数据

## 输出类别

变更内容按以下类别进行组织：

| 类别 | 描述 | 适用场景 |
|----------|-------------|-----------|
| **新功能** | 全新的功能特性 | 新界面、新按钮、新能力 |
| **增强功能** | 对现有功能的改进 | 更快、更好、更多选项 |
| **错误修复** | 已解决的问题 | 之前无法正常运行的功能现已修复 |
| **变更** | 行为调整 | 功能运作方式发生变化 |
| **破坏性变更** | 需要用户采取行动的变更 | 必须更新设置或进行数据迁移 |
| **其他** | 杂项更新 | 文档更新、用户可能察觉到的内部改进 |

## 输入要求

该技能需要以下信息：

1. **仓库路径**（可选）：默认为当前目录
2. **范围指定**（以下任选其一）：
- `from_tag` 和 `to_tag`：比较两个标签（tag）之间的差异
- `since_tag`：从指定标签到 HEAD 的所有变更
- `last_n_commits`：分析最近的 N 次提交（默认值：50）
3. **远程仓库类型**（可选）：`github`、`bitbucket` 或 `local`（自动检测）

**支持的输入格式**：

自然语言：
- "生成从 v1.0.0 到 v1.1.0 的发布说明"
- "自上次发布以来有哪些变化？" - “展示最近 30 次提交中的更新内容”

结构化 JSON：
```json
{
"repo_path": "C:\\Projects\\MyApp",
"from_tag": "v1.0.0",
"to_tag": "v1.1.0"
}
```

## 分析原理

### 第 1 步：收集提交记录
从 Git 仓库中收集指定范围内的所有提交记录。

### 第 2 步：读取完整差异（Diffs）
针对每次提交，读取实际的代码变更内容（新增、删除、修改）。 ### 步骤 3：解读变更
将技术性变更转化为通俗易懂的描述：
- `+ showWelcomeMessage = true` → “应用启动时显示欢迎信息”
- 删除了登录重试逻辑 → “移除了自动登录重试功能”

### 步骤 4：整合变更
归并相关变更并剔除冗余信息：
- 若某功能先添加后移除，则不予提及
- 若某数值发生多次变更，仅保留最终状态
- 将相关的提交合并为单条描述

### 步骤 5：分类
根据以下标准将各项变更归入相应类别：
- 提交信息的关键词（如 feat、fix、enhancement 等）
- 代码变更类型（如新增文件视为功能新增，删除代码视为移除）
- 破坏性变更（Breaking Change）的标识

### 步骤 6：格式化输出
生成整洁的 Markdown 内容，包含：
- 清晰的类别标题
- 简洁的要点列表
- 可选的脚注
